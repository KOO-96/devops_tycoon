## 4.2 게임 개요

- **게임 한 줄 소개:** 인프라 다이어그램을 직접 짓고 장애를 진단·복구하며 회사를 키우는 DevOps 경영 시뮬레이션.
- **장르:** 경영/타이쿤 시뮬레이션 + 시스템 진단 퍼즐 (인프라 매니지먼트).
- **핵심 콘셉트:** 화면에 그려지는 **인프라 구조 자체가 게임판**이다. 플레이어는 서버·LB·캐시·DB를 배치·연결하고, 트래픽 증가로 발생하는 병목과 장애를 로그/메트릭/트레이스로 진단하여 해결한다.
- **목표 사용자:**
  - 개발/인프라 직군 및 지망생 (실무 감각을 게임으로 체험).
  - 타이쿤·시뮬레이션 게임 애호가.
  - CS/DevOps를 학습 중인 학생.
- **플레이어 역할:** 스타트업의 창업자 겸 인프라 총괄. AI CTO의 조언을 받아 기술 의사결정을 내린다.
- **핵심 경험:**
  1. "왜 느려졌지?"를 데이터로 추적하는 **진단의 쾌감**.
  2. 여러 합리적 선택 사이에서 **트레이드오프를 저울질**하는 긴장.
  3. 장애를 넘기고 회사가 성장하는 **누적적 성취**.
- **경쟁/참고 게임:** Factorio(구조=게임판), Opus Magnum/SpaceChem(경로·병목 최적화), Two Point Hospital(경영+이벤트), Mini Metro(네트워크 시각화), 실무 도구 Grafana/Datadog(계측 UI 참고).
- **DevOps Tycoon 차별점:**
  - 장애가 "게임 오버"가 아니라 **핵심 반복 콘텐츠**다.
  - 하나의 문제에 **복수의 정답과 각기 다른 부작용**이 존재한다.
  - AI CTO는 정답을 강요하지 않고 **시뮬레이션이 계산한 사실만** 근거로 조언한다.

## 4.3 핵심 디자인 원칙

| # | 원칙 | 구체적 구현 지침 |
|---|------|-----------------|
| P1 | **교육 게임처럼 보이지 않는다** | 용어를 퀴즈로 묻지 않는다. 지식은 문제 해결 과정에서 자연히 습득된다. 튜토리얼도 실제 장애 시나리오로 진행한다. |
| P2 | **인프라 구조 자체가 게임판이다** | 모든 상태(부하·장애·트래픽)는 캠퍼스 위 노드/엣지에 시각적으로 표현된다. 별도 표가 아니라 게임판에서 읽힌다. |
| P3 | **장애는 실패 화면이 아니라 핵심 콘텐츠다** | 장애는 즉시 실패 화면이나 강제 종료로 전환되지 않으며, [GD-001](#45-게임-시간-구조)의 Pause 정책에 따라 플레이어가 분석·대응할 수 있다. 진단·대응·복구·Postmortem이 하나의 플레이 사이클이다. |
| P4 | **하나의 문제에 하나의 정답만 있지 않다** | 각 장애는 최소 2개 이상의 합리적 대응 경로를 가진다(예: 스케일아웃 vs 캐시 도입 vs 쿼리 최적화). |
| P5 | **모든 기술 도입에는 비용·부작용이 있다** | 기술 도입은 자금/운영 복잡도/기술 부채 중 최소 하나를 증가시킨다. 무료 개선은 없다. |
| P6 | **문제 해결은 새로운 병목을 만들 수 있다** | 상류 병목 해소 시 하류로 부하가 전가되도록 시뮬레이션이 계산한다(예: App 스케일아웃 → DB 커넥션 고갈). |
| P7 | **장애 전 확인 가능한 징후가 존재한다** | 모든 장애는 발동 전 관측 가능한 선행 지표(메트릭 상승·로그 경고·큐 적체)를 노출한다. 무징후 즉사 금지. |
| P8 | **AI CTO는 게임 상태를 임의로 만들지 않는다** | CTO는 Simulation이 산출한 상태만 읽는다. 장애 원인·수치를 생성하거나 확정 단언하지 않는다. |

## 4.4 핵심 게임 루프

전체 흐름:

```
기능 개발 → 사용자/요청 증가 → 병목·이상 신호 → 로그·메트릭·트레이스 분석
→ 해결 방법 선택 → 시스템 상태 변화 → 장애 복구 or 악화 → Postmortem → 회사·시스템 성장
```

각 단계 정의:

### 단계 1 — 서비스 기능 개발
- **플레이어가 보는 정보:** 개발 백로그, 기능별 예상 효과(사용자 유입/매출), 소요 시간, 기술 부채 영향.
- **행동:** 기능 선택 및 개발 착수, 배포 예약.
- **시스템 변화:** 개발 진행률 증가, 완료 시 신규 기능 활성화 및 사용자 유입 계수 상승.
- **성공 조건:** 배포 완료 및 정상 반영.
- **실패 조건:** 배포 실패(테스트/헬스체크 불통과) → 자동 또는 수동 Rollback 대상.
- **다음 단계 전이:** 기능 배포 후 사용자/요청 증가 시작.

### 단계 2 — 사용자 및 요청 증가
- **보는 정보:** 실시간 RPS, 활성 사용자 수, 유입 추세 그래프.
- **행동:** 관망 또는 사전 증설(선제 대응).
- **시스템 변화:** 요청량 증가 → 각 노드 자원 사용률 상승.
- **성공 조건:** 자원 사용률이 안전 임계 이하 유지.
- **실패 조건:** 없음(정보 수집 단계).
- **전이:** 특정 노드 사용률이 경고 임계(TBD, 예: 70%) 초과 시 이상 신호 단계로.

### 단계 3 — 병목·이상 신호 발생
- **보는 정보:** 경고 상태 노드 하이라이트, 응답 지연 상승, 큐 길이 증가, 에러율 상승.
- **행동:** 상세 패널 열람, 계측(로그/메트릭/트레이스) 확인.
- **시스템 변화:** 노드 상태 `Healthy → Warning` 전환.
- **성공 조건:** 원인 노드/지표 특정.
- **실패 조건:** 무대응 방치 시 `Warning → Critical` 악화.
- **전이:** 플레이어가 분석 도구를 열면 분석 단계로.

### 단계 4 — 로그·메트릭·트레이스 분석
- **보는 정보:** 로그(필터/검색), 시계열 메트릭, 요청 트레이스(스팬별 지연).
- **행동:** 지표 상관관계 추론, 병목 구간 지목.
- **시스템 변화:** 없음(읽기 전용 관측).
- **성공 조건:** 근본 원인(root cause) 가설 수립.
- **실패 조건:** 오진 시 잘못된 해결책 선택 위험.
- **전이:** 해결 방법 선택 UI 진입.

### 단계 5 — 해결 방법 선택
- **보는 정보:** 적용 가능한 조치 목록, 각 조치의 비용/소요 시간/예상 효과/부작용, AI CTO 조언.
- **행동:** 조치 1개 이상 선택 및 실행.
- **시스템 변화:** 조치 실행 예약, 자금 차감, 소요 시간 카운트다운.
- **성공 조건:** 조치 실행 개시.
- **실패 조건:** 자금 부족/전제 미충족으로 조치 불가.
- **전이:** 조치 완료 시 상태 변화 단계로.

### 단계 6 — 시스템 상태 변화
- **보는 정보:** 조치 반영 후 메트릭 변화, 상태 색상 갱신.
- **행동:** 결과 관측, 추가 대응 여부 판단.
- **시스템 변화:** Simulation이 조치 효과 및 **파생 병목(P6)** 재계산.
- **성공 조건:** 대상 지표 정상 범위 회복.
- **실패 조건:** 미해결 또는 신규 병목 발생.
- **전이:** 회복 시 복구 단계, 악화 시 장애 심화.

### 단계 7 — 장애 복구 또는 악화
- **보는 정보:** 장애 타임라인, 영향받은 사용자/매출, 복구 진행률.
- **행동:** 복구 조치 반복 또는 Rollback.
- **시스템 변화:** 복구 시 신뢰도 회복, 악화 시 사용자/투자자 신뢰도 하락.
- **성공 조건:** 장애 종료(모든 노드 `Healthy`).
- **실패 조건:** 장기 장애 지속 → 신뢰도 붕괴 위험([4.15](#415-승리실패-조건)).
- **전이:** 장애 종료 시 Postmortem.

### 단계 8 — Postmortem
- **보는 정보:** 장애 타임라인 요약, 원인, 취한 조치, 손실 지표, CTO 코멘트.
- **행동:** 재발 방지 항목 채택(선택 시 소폭 보너스/부채 감소), 기록 확인.
- **시스템 변화:** 학습 보상 반영, 향후 동일 장애 발생 확률/난이도 조정 훅.
- **성공 조건:** Postmortem 확인 완료.
- **실패 조건:** 없음.
- **전이:** 성장 단계로.

### 단계 9 — 회사와 시스템 성장
- **보는 정보:** 누적 성과, 성장 단계 진행률, 승급 조건.
- **행동:** 다음 기능 개발 계획, 조직/기술 투자.
- **시스템 변화:** 자원 갱신, 승급 조건 충족 시 [4.7 성장 단계](#47-성장-단계) 전이.
- **성공 조건:** 승급 조건 충족.
- **실패 조건:** 자원 붕괴 시 게임 오버.
- **전이:** 단계 1로 순환.

## 4.5 게임 시간 구조

> **GD-001 결정: 시간 구조는 Confirmed, 세부 수치는 Proposed.** 상세·근거는 [program-decisions.md §1](./program-decisions.md#1-gd-001--게임-시간-구조-confirmed) 참조.
> 모든 시간은 **Tick(canonical)**으로 저장하며 Frontend가 게임 시간으로 변환 표시한다.

| 항목 | 정의 | 상태 |
|------|------|------|
| 실시간 진행 | 게임은 실시간 기반 + 고정 Tick으로 진행(턴제 아님). 결과는 wall-clock이 아닌 Tick으로 계산 | **Confirmed** |
| 일시정지(속도 0) | 시간 정지. 정지 중 관측/계획/명령 예약 가능. 시간 소요 조치는 재개 시 진행 | **Confirmed** |
| 배속 1× / 2× / 4× | 같은 실제 프레임에서 처리하는 Tick 수 배율에만 영향. 계산 결과는 불변 | **Confirmed** |
| 게임 Tick | 시뮬레이션의 원자적 결정론 단위. 1 Tick = 200 ms(1× 기준) | 구조 Confirmed / 값 Proposed |
| 게임 시간 단위 | 1 게임일 = 300 Tick, 1 스프린트 = 7 게임일 | 구조 Confirmed / 값 Proposed |
| 이벤트 발생 시간 | Tick 기준 스케줄/조건으로 발동. `duration_ticks`/`cooldown_ticks` 등 | 구조 Confirmed / 값 Proposed |
| 장애 대응 제한 시간 | `response_window_ticks`. 상대등급 짧음/보통/긺 = 30/90/300 Tick | 구조 Confirmed / 값 Proposed |
| 개발 작업 소요 시간 | `work_duration_ticks` | 구조 Confirmed / 값 Proposed |
| 배포 작업 소요 시간 | `deploy_duration_ticks` | 구조 Confirmed / 값 Proposed |

> **일시정지 정책:** 일시정지 중에도 플레이어는 분석·계획·조치 예약이 가능해야 한다(진단 게임 특성상). 단, 시간이 소요되는 조치의 실제 진행은 재개 후 이루어진다.
> **저장·복원:** `current_tick`, `simulation_time`, `speed`, `paused`, `rng_state`를 영속화하며, 복원 후 동일 Tick 진행 시 동일 결과를 보장한다(Simulation 재현성).

## 4.6 플레이어 자원

각 자원의 의미와 변화 조건. 초기값·계수는 Simulation 담당이 밸런싱하며 현재는 `TBD`.

| 자원 | 의미 | 증가 조건 | 감소 조건 |
|------|------|-----------|-----------|
| 자금(Cash) | 운영 재원 | 매출, 투자 유치 | 서버 비용, 기술 도입, 인건비 |
| 사용자 수(Users) | 활성 사용자 | 기능 출시, 안정적 서비스, 마케팅 이벤트 | 장애·저성능으로 이탈 |
| 사용자 신뢰도(User Trust) | 서비스 만족/신뢰 | 안정 운영, 빠른 복구 | 장애 지속, 느린 응답, 데이터 유실 |
| 투자자 신뢰도(Investor Trust) | 투자 유치 가능성 | 성장 지표 달성, 목표 충족 | 반복 장애, 성장 정체, 파산 위기 |
| 개발 생산성(Dev Productivity) | 기능 개발 속도 계수 | 조직 확대, 부채 상환, 낮은 피로도 | 높은 기술 부채, 높은 피로도 |
| 기술 부채(Tech Debt) | 누적 미상환 설계 비용 | 임시방편 조치, 급속 성장 | 리팩터링/상환 투자 |
| 운영 복잡도(Ops Complexity) | 시스템 관리 난이도 | 기술 스택 추가, 노드 증가 | 통합·정리, 자동화 도입 |
| 직원 피로도(Team Fatigue) | 번아웃 지표 | 잦은 장애 대응, 야근성 크런치 | 휴식, 인력 충원, 자동화 |
| 장애율(Incident Rate) | 단위 시간당 장애 빈도(파생 지표) | 높은 부채·복잡도·부하 | 안정화 투자, 관측성 강화 |
| 응답 속도(Latency) | 사용자 체감 지연(파생 지표) | 병목·부하 | 스케일·캐시·최적화 |
| 서버 비용(Server Cost) | 인프라 운영 비용 | 노드/사양 증가 | 축소, 효율화 |
| 매출(Revenue) | 수익 흐름 | 사용자 수 × 전환/과금 계수 | 사용자 이탈, 장애 중 매출 손실 |

> **파생 지표 규칙:** 장애율·응답 속도·매출은 플레이어가 직접 설정하지 않고 Simulation이 다른 상태로부터 계산한다. AI CTO는 이 값을 읽되 변경하지 않는다.

## 4.7 성장 단계

| # | 단계 | 시작 조건 | 주요 목표 | 사용 가능 기술 | 주요 병목 | 주요 이벤트 | 조직 규모 | 승급 조건 | 실패 가능성 |
|---|------|-----------|-----------|----------------|-----------|-------------|-----------|-----------|-------------|

| 4 | 대규모 서비스 | 단계3 승급 | 고가용성 | 오토스케일, 샤딩(Post-MVP) | 카스케이딩 장애, 핫샤드 | 지역 장애, 대규모 배포 사고 | 21~100명 | 가용성 목표 `TBD` | 카스케이딩 붕괴, 데이터 유실 |
| 5 | 글로벌 플랫폼 | 단계4 승급 | 글로벌 확장 | Multi-Region, Global DB, Service Mesh(Post-MVP) | 지역 간 지연, 일관성 문제 | 리전 장애, 규제 이벤트 | 100명+ | 글로벌 SLA `TBD` | 글로벌 동시 장애 |

> **MVP 범위:** 단계 1~2를 MVP 캠페인의 핵심으로 삼고, 단계 3의 일부(Black Friday, DB 커넥션 고갈)까지 첫 캠페인에 포함한다. 단계 4~5의 고급 기술은 [4.8](#48-mvp-범위) 기준 Post-MVP.

## 4.8 MVP 범위

### MVP 포함 — 구성 요소
Users, Load Balancer, App Server, Redis, PostgreSQL, 기본 로그, 기본 메트릭, 서버 비용, 사용자 만족도, 기술 부채, 기능 개발, 배포, Rollback, 장애 대응, Postmortem, AI CTO 2명.

### MVP 포함 — 장애
CPU 과부하, Load Balancer 트래픽 불균형, DB Connection Pool 고갈, Slow Query, Redis Cache Miss, Stale Cache, 메모리 부족/Memory Leak, 배포 실패, 서버 다운.

### MVP 제외 → Post-MVP (삭제 아님)
Kafka, Service Mesh, Multi Region, Global Database, 복잡한 Kubernetes 운영, 커뮤니티 시나리오 제작기, 멀티플레이, 대규모 조직 관리.

> **경계:** 위 Post-MVP 항목은 [4.7 성장 단계](#47-성장-단계) 3~5에 배치되며, 데이터/문서에서 제거하지 않고 "Post-MVP"로 표시만 한다.

### MVP 정의 요약 표

| 구분 | 포함(MVP) | 제외(Post-MVP) |
|------|-----------|----------------|
| 인프라 | Users, LB, App, Redis, PostgreSQL | Kafka, Service Mesh, Multi-Region, Global DB |
| 운영 | 로그, 메트릭, 배포, Rollback, Postmortem | 복잡한 K8s 운영 |
| 조직 | AI CTO 2명 | 대규모 조직 관리, 멀티플레이 |
| 콘텐츠 | 고정 첫 캠페인 | 커뮤니티 시나리오 제작기 |

## 4.9 프론트엔드 요구사항

기준 형태: **아이소메트릭 캠퍼스**(부지 위에 건물/서버 랙 배치, 노드 간 연결로 인프라 구성).

### 화면·기능 및 Acceptance Criteria

각 항목의 `AC`는 검증 가능해야 한다.

#### FE-1 아이소메트릭 캠퍼스
- AC: 캠퍼스는 아이소메트릭 뷰로 렌더링되고, 배치된 노드/엣지가 표시된다.
- AC: 각 노드는 종류별로 구분되는 아이콘/랙 형태를 가진다.

#### FE-2 카메라 이동 / FE-3 확대·축소
- AC: 드래그(또는 방향키)로 화면을 이동할 수 있어야 한다.
- AC: 휠/버튼으로 최소 `TBD`× ~ 최대 `TBD`× 범위에서 확대·축소할 수 있어야 한다.

#### FE-4 건물 배치 / FE-5 서버 랙 배치
- AC: 플레이어는 App Server를 2대 이상 배치할 수 있어야 한다.
- AC: 배치 시 자금이 부족하면 배치가 차단되고 사유가 표시되어야 한다.

#### FE-6 인프라 연결
- AC: 플레이어는 Load Balancer와 App Server를 연결할 수 있어야 한다.
- AC: 연결되지 않은 서버에는 요청이 전달되지 않아야 한다(요청 패킷 애니메이션 미표시 + 트래픽 0).
- AC: 허용되지 않는 연결(예: LB → PostgreSQL 직접)은 생성이 거부되어야 한다.

#### FE-7 요청 패킷 애니메이션
- AC: 요청은 Users → LB → App → (Redis/PostgreSQL) 경로를 따라 시각적으로 흐른다.
- AC: 패킷 흐름 밀도는 현재 RPS에 비례해 변한다.

#### FE-8 서버 상태 표현
- AC: 서버별 CPU, 메모리, Queue 길이를 상세 패널에서 확인할 수 있어야 한다.
- AC: 상태는 `Healthy / Warning / Critical / Down` 4단계로 색상 구분된다.
- AC: 서버 상태 변경은 WebSocket 이벤트 수신 후 화면에 반영되어야 한다.

#### FE-9 장애 시각 효과
- AC: Warning 이상 노드에는 시각 경고(아이콘/색/펄스)가 표시된다.
- AC: 트래픽 불균형 발생 시 서버별 요청량 차이를 화면에서 확인할 수 있어야 한다.

#### FE-10 상단 HUD
- AC: 자금, 사용자 수, 신뢰도, 현재 게임 시간, 배속 상태가 상시 표시된다.

#### FE-11 좌측 기능 메뉴
- AC: 배치/연결/개발/배포/조치 등 주요 액션에 접근할 수 있다.

#### FE-12 우측 목표·경고 패널
- AC: 현재 챕터 목표와 활성 경고/장애 목록이 표시된다.
- AC: DB Connection 사용률이 80%를 넘으면 Warning 상태가 표시되어야 한다.

#### FE-13 하단 상세 패널
- AC: 선택된 노드의 상세 지표·가능한 조치가 표시된다.

#### FE-14 로그 화면 / FE-15 메트릭 화면 / FE-16 트레이스 화면
- AC(로그): 시간·레벨·소스로 필터/검색할 수 있어야 한다.
- AC(메트릭): 노드별 시계열(CPU/메모리/Queue/Latency)을 조회할 수 있어야 한다.
- AC(트레이스): 단일 요청의 스팬별 지연을 확인할 수 있어야 한다.

#### FE-17 AI CTO 대화 영역
- AC: CTO 발언이 대화 형태로 표시되고, 플레이어가 조언을 요청할 수 있다.
- AC: CTO 발언에는 근거가 된 지표가 함께 표시된다(사실 근거 표기).

#### FE-18 에러·로딩·빈 상태
- AC: 데이터 로딩 중/실패/빈 상태 각각에 대해 구분된 UI가 표시된다.

#### FE-19 WebSocket 재접속 상태
- AC: 연결 끊김 시 "재접속 중" 표시가 뜨고, 복구 시 최신 Snapshot으로 상태를 동기화한다.
- AC: 재접속 후 화면 상태가 서버 권위 상태와 일치해야 한다(불일치 없음).

## 4.10 백엔드 요구사항

Backend는 API/세션/영속화/실시간 전달을 담당한다.

| # | 항목 | 요구사항 |
|---|------|----------|
| BE-1 | 게임 세션 생성 | 새 세션 생성 시 Seed·초기 상태를 확정하여 반환한다. |
| BE-2 | 게임 세션 조회 | 세션 ID로 현재 세션 메타/상태 요약을 조회할 수 있다. |
| BE-3 | 게임 상태 Snapshot | 특정 시점의 전체 게임 상태 Snapshot을 제공/저장한다. |
| BE-4 | 플레이어 명령 처리 | 명령을 검증 후 Simulation에 전달하고 결과를 반영한다. |
| BE-5 | 상태 저장 / BE-6 상태 불러오기 | 순수 게임 상태를 영속화하고 동일하게 복원한다. |
| BE-7 | WebSocket 이벤트 | 상태 변화·장애·조치 결과를 실시간 이벤트로 브로드캐스트한다. |
| BE-8 | AI CTO 연동 | Simulation 상태를 CTO 모듈에 전달하고 CTO 응답을 중계한다. |
| BE-9 | PostgreSQL | 세션/Snapshot/이벤트 로그의 영속 저장소. |
| BE-10 | Redis | 세션 캐시/실시간 상태/발행-구독 채널. |
| BE-11 | 오류 코드 | 표준 오류 코드 체계를 정의하고 일관되게 반환한다. |
| BE-12 | 명령 멱등성 | 동일 command_id 재수신 시 중복 적용하지 않는다. |
| BE-13 | API 버전 관리 | API에 버전 접두(예: `/v1`)를 둔다. |
| BE-14 | DB 마이그레이션 | 스키마 변경을 마이그레이션으로 관리한다. |

### 책임 경계 (중요)
> **Backend는 시뮬레이션 결과를 임의로 계산하지 않는다.** 부하·장애·자원 변화 등 게임 규칙 계산은 전적으로 Simulation 모듈이 수행하며, Backend는 그 결과를 **검증·저장·전달**만 한다. Backend가 상태 값을 직접 조작하는 것을 금지한다.

### Acceptance Criteria (예시)
- AC: 동일 command_id로 명령을 2회 보내면 상태는 1회 적용된 결과와 동일해야 한다(멱등성).
- AC: 세션 저장 후 불러오면 저장 시점과 동일한 게임 상태가 복원되어야 한다.
- AC: 잘못된 명령은 표준 오류 코드와 함께 거부되고, 게임 상태가 변하지 않아야 한다.
- AC: 상태 변화 발생 시 관련 WebSocket 이벤트가 발행되어야 한다.

## 4.11 Simulation 요구사항

Simulation은 **게임 규칙·사실·결과를 계산**하는 권위 모듈이다.

| 영역 | 계산 책임 |
|------|-----------|
| 시간 | 게임 Tick, 게임 시간, 배속, 일시정지 처리 |
| 트래픽 | 사용자 생성, 요청 생성, 요청 경로 이동, LB 분배 |
| 자원 | CPU/메모리/네트워크 사용량, Queue 적체 |
| 데이터 계층 | DB Connection Pool, Redis Cache Hit/Miss |
| 신뢰성 | Timeout, Retry |
| 장애 | 장애 원인, 장애 발생 조건 판정 |
| 경제 | 기술 효과, 비용, 매출, 기술 부채 |
| 이벤트 | 이벤트 발동 조건 판정 |
| 재현성 | Seed 기반 결정론적 계산, 저장 가능한 순수 게임 상태 |

### 핵심 원칙
- Simulation은 **사실과 결과를 계산**하고, AI CTO가 사용할 **근거 데이터**를 제공한다.
- **결정론:** 동일 Seed + 동일 명령 순서 → 동일 결과. (Date.now/난수 직접 사용 금지, Seed 기반 PRNG 사용.)
- **파생 병목(P6):** 상류 병목 해소가 하류 부하로 전가되는 관계를 명시적으로 모델링한다.
- **선행 징후(P7):** 장애 발동 전 관측 가능한 지표를 반드시 노출한다.

### Acceptance Criteria (예시)
- AC: 동일 Seed와 동일 명령 순서에서는 동일한 장애 결과가 발생해야 한다.
- AC: App Server를 스케일아웃하면 App CPU는 하락하고, 조건 충족 시 DB Connection 사용률이 상승해야 한다(파생 병목).
- AC: DB Connection 사용률이 임계(80%, TBD 조정 가능)에 도달하면 Warning 신호가 상태에 기록되어야 한다.
- AC: 저장된 순수 게임 상태로부터 복원 후 이어서 Tick을 진행하면, 중단 없이 진행한 경우와 동일한 결과가 나와야 한다.

## 4.12 AI CTO 기획

MVP에서 최소 2명의 CTO를 정의한다.

### CTO-A: 안정성 중심 (코드네임: "가디언")
| 항목 | 정의 |
|------|------|
| 성격 | 신중, 보수적, 위험 회피 |
| 말투 | 차분하고 단정적이지 않음. "~할 수 있습니다", "우선 확인하죠" |
| 운영 철학 | 가용성·데이터 무결성 최우선. 성장보다 안정. |
| 선호 해결 | 관측성 강화, 점진적 스케일, Rollback, 부채 상환 |
| 반대 해결 | 검증 없는 급속 배포, 임시방편, 무리한 트래픽 유치 |
| 위험 설명 방식 | 최악 시나리오와 확률적 표현으로 경고 |
| 과거 선택 기억 | 이전 장애/조치를 인용해 재발 위험 상기 |
| 충돌 조건 | 성장 중심 CTO가 속도를 위해 안정성 희생 제안 시 |
| 질문 방식 | "데이터를 먼저 볼까요? 어떤 지표가 튀었나요?" |
| 정답 공개 범위 | 관측된 사실 기반 가설·트레이드오프까지. 미관측 원인 단정 금지. |
| 절대 금지 | 시뮬레이션이 산출하지 않은 원인/수치 생성, 단일 정답 강요 |

### CTO-B: 성장 중심 (코드네임: "부스터")
| 항목 | 정의 |
|------|------|
| 성격 | 공격적, 낙관적, 속도 지향 |
| 말투 | 활기차고 추진력 있음. "지금 밀어붙이죠", "기회입니다" |
| 운영 철학 | 성장·시장 선점 우선. 일부 부채는 감수. |
| 선호 해결 | 빠른 스케일아웃, 기능 우선 출시, 공격적 마케팅 |
| 반대 해결 | 과도한 신중함, 성장 지연시키는 완벽주의 |
| 위험 설명 방식 | 기회비용 중심. "지금 안 하면 잃는 것"을 강조 |
| 과거 선택 기억 | 이전 성공 사례를 인용해 과감한 선택 지지 |
| 충돌 조건 | 안정성 중심 CTO가 성장 기회를 지연시킬 때 |
| 질문 방식 | "이 병목만 넘기면 성장할 수 있는데, 감수할까요?" |
| 정답 공개 범위 | 관측된 사실 기반 대안 제시. 미관측 원인 단정 금지. |
| 절대 금지 | 시뮬레이션 사실 왜곡, 위험 은폐, 단일 정답 강요 |

### AI CTO 공통 원칙 (필수)
1. AI CTO는 **실제 장애 원인을 임의로 생성하지 않는다.**
2. **Simulation이 제공한 상태만** 근거로 사용한다.
3. **관측할 수 없는 정보를 확정적으로 알려주지 않는다.** (미관측 사항은 가설로만 제시.)
4. **하나의 정답만 강요하지 않는다.**
5. 선택의 **장점과 위험을 함께** 설명한다.

> **경계 재확인:** CTO는 Simulation 상태의 소비자다. 상태를 읽고 해석·조언만 하며, 상태를 변경하거나 새 사실을 만들지 않는다([4.3 P8](#43-핵심-디자인-원칙), [4.11](#411-simulation-요구사항)).

## 4.13 이벤트 기획 기준

이벤트가 승인되려면 아래 기준을 모두 충족해야 한다.

| EV-8 | 보상·페널티가 과도하지 않은가? | 밸런스 범위 내(기준 TBD) |
| EV-9 | 동일 이벤트 반복 방지 규칙이 있는가? | 쿨다운/1회성/조건 재무장 규칙 명시 |

### 복구 가능 상태 vs 게임 오버 구분
- **복구 가능:** 장애·경고·자원 하락은 조치로 되돌릴 수 있는 한 게임 오버가 아니다. 장애는 콘텐츠다(P3).
- **게임 오버:** 파산 확정, 신뢰도 붕괴 임계 도달, 복구 불가 데이터 유실 중 하나가 확정될 때.
- AC: 자금이 일시적으로 음수여도 유예 기간 내 회복하면 게임은 계속되어야 한다.
- AC: 게임 오버 판정은 Simulation 상태 기준으로만 발생하며, UI/CTO가 임의로 선언하지 않는다.

## 4.16 Acceptance Criteria (측정 가능 기준 원칙)

모든 주요 기능은 **검증 가능한 조건**을 가진다. 아래는 대표 기준이며, 각 절의 AC와 함께 회귀 테스트 기준으로 사용한다.

- AC: 서버별 CPU, 메모리, Queue 길이를 확인할 수 있어야 한다.
- AC: DB Connection 사용률이 80%를 넘으면 Warning 상태가 표시되어야 한다.
- AC: 최근 배포 이후 오류율이 증가하면 Rollback을 실행할 수 있어야 한다.
- AC: Rollback 완료 후 이전 애플리케이션 버전이 복구되어야 한다.
- AC: 동일 Seed와 동일 명령 순서에서는 동일한 장애 결과가 발생해야 한다.
- AC: 연결되지 않은 서버에는 요청이 전달되지 않아야 한다.
- AC: 동일 command_id 재전송 시 상태가 중복 적용되지 않아야 한다.
- AC: WebSocket 재접속 후 화면 상태가 서버 권위 상태와 일치해야 한다.

> **금지 표현:** "잘 작동해야 한다", "재미있어야 한다", "잘 보여야 한다" 같은 비측정 표현은 AC로 인정하지 않는다.

| **DevCTO** | 아키텍처·통합·최종 품질 승인 | 아키텍처 설계 검토, 모듈 책임·경계, 역할 간 통합, 최종 품질 게이트/승인 | 각 역할 설계·PR, Ops 검토 결과 | 아키텍처 결정, 통합 승인, 최종 품질 승인 | 전 역할, Ops | 검토 없는 대규모 변경 승인 금지 | 아키텍처 정합성 확인, 통합·최종 품질 승인 | 전 영역 경계 |
| **Event** | 이벤트 데이터 상세 설계 | 개별 이벤트/장애 시나리오 데이터 | 승인 기준·Sim 훅 | 이벤트 데이터셋 | Simulation(발동 판정) | [4.13](#413-이벤트-기획-기준) 기준 미충족 이벤트 병합 금지 | EV-1~10 전부 통과 | 4.13 |
| **Infra** | 게임 실행 인프라(실 운영) | 배포/CI/런타임 환경 | 앱 산출물 | 실행 환경 | Backend/Frontend 빌드 | 게임 속 인프라와 실 인프라 혼동 금지 | 실행/배포 파이프라인 동작 | 운영 기준(별도) |

> **경계 재강조:** 게임 속 "Kubernetes"는 콘텐츠이고, 실제 운영용(예: k3s)은 Infra 담당의 실 인프라다. 문서/코드에서 둘을 혼동하지 않는다.
> **AI CTO 책임 3분할:** ① **대화·조언 원칙**은 Program이 정의(4.12), ② **근거 데이터(CTO Evidence)**는 Simulation이 사실로 생성, ③ **실제 연동(LLM 호출·중계)**은 Backend가 담당한다. 세 역할 모두 [4.12 공통 원칙](#412-ai-cto-기획)(Sim 사실만 근거, 미관측 단정 금지, 단일정답 강요 금지)을 준수한다.
