## EVT-LB-001 Load Balancer 트래픽 불균형

- 이벤트 유형: 기술 장애
- 관련 기술: Load Balancer, App Scaling, Health Check
- 적용 게임 단계: 2~3
- 이벤트 목적: 서버 수만 늘려서는 트래픽이 고르게 분산되지 않는다는 점을 체감시킨다. "증설 ≠ 해결"을 학습.

### 발동 조건 (Trigger)
- App Server 2대 이상 + Load Balancer 활성.
- 분산 설정 오류(예: 잘못된 Sticky Session, 가중치 편향) 또는 일부 서버 Health Check 실패로 트래픽 제외.
- 서버별 요청 비율 차이 ≥ 임계(Proposed: 40%p) 가 지속 시간(Proposed: 짧음~보통) 이상 유지.

### 발동 제외 조건 (Suppression)
- App Server 1대 이하이거나 LB 미도입.
- 서버별 요청 비율 차이가 임계 미만.
- 동일 이벤트 쿨다운 중.

### 사전 징후 (Warning Signs)
- 특정 App Server CPU만 지속 상승, 다른 App Server는 낮게 유지.
- 서버별 Request Rate 격차 확대.
- 편중 서버의 Queue 길이 증가, Latency 상승.

### 플레이어가 확인할 수 있는 정보
- 모니터링 없을 때: 전체 응답 지연 상승, 간헐 오류만 감지(원인 서버 특정 어려움).
- 모니터링 있을 때: 서버별 Request Rate/CPU/Queue 비교 그래프로 편중 서버 특정 가능.

### 대응 제한 시간 (Response Window)
- Proposed: 보통. 방치 시 편중 서버가 Critical → 오류율 급증. (절대값 TBD, GD-001 의존)

### 가능한 대응 방법 (≥2)
| 대응 | 장점 | 부작용/비용/복잡도 |
|------|------|--------------------|
| LB 분산 알고리즘 변경(RR/Least-Conn) | 근본 해결 | 적용 시간 필요, 순간 재분배로 짧은 지연 |
| Sticky Session 해제 | 편중 원인 제거 | 세션 의존 기능 영향 가능 |
| Health Check 설정 수정 | 오제외 서버 복귀 | 잘못 조정 시 비정상 서버 편입 위험 |
| 서버 추가 | 단기 처리량 증가 | 설정 오류 유지 시 신규 서버도 미활용, 비용↑(P5) |
| 특정 서버 재시작 | 일시적 완화 | 근본 원인 미해결, 재발 |

### 결과 판정
- 성공 조건: 서버별 요청 비율 차이 ≤ 허용(Proposed: 15%p), 오류율 정상, Queue 감소.
- 부분 성공 조건: 편중 완화됐으나 근본 설정 미수정(서버 추가만으로 버팀) → 재발 위험 잔존.
- 실패 조건: 편중 서버 CPU 포화, Timeout·502 오류 증가 지속.

### 결과 영향
- 즉시 결과: 성공 시 Latency·오류율 회복. 실패 시 사용자 신뢰도 하락, 매출 손실.
- 지연 후폭풍 (P6): 서버 증설만으로 해결 시 비용 증가 + 설정 오류 유지 → 다음 트래픽 증가(EVT-EXT-*) 때 재발.
- 보상: 근본 해결 시 소폭 신뢰도 회복, Postmortem 학습 포인트.
- 페널티: 실패 시 사용자 신뢰도 하락(Proposed), 서버 증설 시 서버 비용 증가.

### 반복 제어
- 쿨다운: Proposed 보통(TBD, GD-EVT 시간 확정 의존).
- 동시 발생 가능: EVT-APP-001, EVT-EXT-001/002/003.
- 동시 발생 금지: 동일 LB 대상 중복 인스턴스.
- 반복 방지 조건: 근본 설정 수정 시 재무장까지 조건 리셋; 미수정 시 트래픽 증가마다 재무장.

### 난이도별 수치
| 항목 | Easy | Normal | Hard | 상태 |
|------|------|--------|------|------|
| 발동 요청비율 차 임계 | 55%p | 40%p | 30%p | Proposed |
| 성공 허용 차 | 20%p | 15%p | 10%p | Proposed |
| 대응 제한 시간 | 긺 | 보통 | 짧음 | Proposed |

### Simulation 인터페이스
- 입력: 서버별 Request Rate, CPU, Queue, LB 설정(알고리즘/스티키/가중치), Health Check 상태.
- 출력: 편중 지표(서버별 비율 차), 이벤트 상태(Warning/Critical), 성공·실패 판정, 후폭풍 플래그.

### Acceptance Criteria
- AC: LB 불균형 발생 시 서버별 요청률 차이가 UI에 표시되어야 한다.
- AC: 서버별 요청 비율 차이가 허용 범위 이하로 내려가면 성공 판정되어야 한다.
- AC: 근본 설정 미수정 상태로 서버만 추가한 경우 부분 성공으로 판정되고 재발 플래그가 설정되어야 한다.
- AC: 동일 Seed·명령 순서에서 동일하게 발동/판정되어야 한다.

### 미확정 사항 / Program 승인 상태
- 미확정: 임계 수치 확정, 대응 제한 시간 절대값(GD-001 의존).
- 승인 상태: Program Review.

## EVT-APP-001 App Server CPU 과부하

- 이벤트 유형: 기술 장애
- 관련 기술: App Scaling, Load Balancer
- 적용 게임 단계: 1~3
- 이벤트 목적: 트래픽 증가 → 연산 병목을 체감하고, 수직/수평 확장과 최적화의 트레이드오프를 학습.

### 발동 조건 (Trigger)
- App Server 평균 CPU ≥ Critical 임계(Proposed: 90%)가 지속 시간(Proposed: 짧음) 이상.
- 또는 RPS가 현재 처리 용량 대비 초과.

### 발동 제외 조건
- CPU가 Warning 임계(Proposed: 70%) 미만.
- 오토스케일(Post-MVP) 미도입 상태에서는 수동 대응만 유효(범위 밖 기술 요구 금지).

### 사전 징후
- CPU Warning(70%) 진입, 요청 처리 지연 상승.
- Queue 길이 증가, 일부 요청 Timeout 조짐.

### 플레이어가 확인할 수 있는 정보
- 모니터링 없을 때: 응답이 느려짐, 간헐 오류.
- 모니터링 있을 때: 서버별 CPU 시계열, Queue, Latency, RPS.

### 대응 제한 시간
- Proposed: 짧음~보통. Critical 지속 시 서버 Down(EVT-SRV-001)으로 전이 가능.

### 가능한 대응 방법 (≥2)
| 대응 | 장점 | 부작용/비용/복잡도 |
|------|------|--------------------|
| App Server 수평 확장(추가) | 처리량 즉시 증가 | 서버 비용↑, DB 커넥션 증가로 EVT-DB-001 유발 가능(P6) |
| 인스턴스 사양 상향(수직) | 빠른 완화 | 비용↑, 단일 서버 한계, 재시작 필요 |
| 코드/연산 최적화 | 근본 개선, 비용 절감 | 개발 시간 소요, 생산성 일시 점유 |
| 요청 Rate Limit/기능 제한 | 즉시 부하 감소 | 사용자 경험 저하, 매출 기회 손실 |

### 결과 판정
- 성공 조건: 평균 CPU ≤ 안전(Proposed: 60%), Queue 감소, Timeout 정상.
- 부분 성공 조건: CPU가 Warning 구간(60~70%)에서 유지(추가 여유 부족).
- 실패 조건: CPU 포화 지속, 다수 Timeout, 서버 Down 전이.

### 결과 영향
- 즉시 결과: 성공 시 Latency 회복. 실패 시 사용자 이탈·매출 손실.
- 지연 후폭풍 (P6): 수평 확장으로 해결 시 DB 커넥션 총량 증가 → EVT-DB-001 발동 조건 근접.
- 보상: 최적화 선택 시 기술 부채 감소 소폭, 비용 효율.
- 페널티: 확장만 반복 시 서버 비용·운영 복잡도 증가.

### 반복 제어
- 쿨다운: Proposed 보통.
- 동시 발생 가능: EVT-LB-001, EVT-EXT-001/002/003.
- 동시 발생 금지: 동일 서버 그룹 CPU 중복 인스턴스.
- 반복 방지 조건: 용량 대비 트래픽이 안전 마진 내로 돌아오면 재무장.

### 난이도별 수치
| 항목 | Easy | Normal | Hard | 상태 |
|------|------|--------|------|------|
| Warning CPU | 75% | 70% | 65% | Proposed |
| Critical CPU | 92% | 90% | 85% | Proposed |
| 성공 목표 CPU | 65% | 60% | 55% | Proposed |

### Simulation 인터페이스
- 입력: 서버별 CPU, RPS, 처리 용량, Queue, 확장/최적화 명령.
- 출력: CPU 상태, 이벤트 상태, 성공·실패 판정, DB 커넥션 파생 부하 신호.

### Acceptance Criteria
- AC: 평균 CPU가 Critical 임계를 지속 시간 이상 초과하면 CPU 과부하 이벤트가 발동해야 한다.
- AC: 수평 확장 시 DB 커넥션 총량 증가가 상태에 반영되어야 한다(P6).
- AC: 대응 제한 시간 내 성공 조건 충족 시 실패 페널티가 적용되지 않아야 한다.

### 미확정 사항 / Program 승인 상태
- 미확정: CPU 임계·시간 확정.
- 승인 상태: Program Review.

## EVT-APP-002 App Server 메모리 부족 / Memory Leak

- 이벤트 유형: 기술 장애
- 관련 기술: App Scaling, 배포
- 적용 게임 단계: 2~3
- 이벤트 목적: 순간 부하가 아닌 **시간에 따라 누적**되는 장애(누수)를 진단·구분하는 경험 제공.

### 발동 조건 (Trigger)
- 메모리 사용률이 시간에 따라 단조 증가(누수 패턴) 또는 순간 부족.
- 메모리 사용률 ≥ Critical(Proposed: 90%)에서 OOM 위험.

### 발동 제외 조건
- 메모리 사용률 Warning(Proposed: 75%) 미만이고 증가 추세 없음.
- 최근 재시작/재배포 직후 안정 구간.

### 사전 징후
- 메모리 사용률이 시간에 비례해 우상향(누수 시그니처).
- GC 빈도 증가, Latency 점진 상승, 재시작 후 일시 회복 후 재증가.

### 플레이어가 확인할 수 있는 정보
- 모니터링 없을 때: 주기적으로 느려지다 재시작하면 잠시 회복(원인 불명).
- 모니터링 있을 때: 메모리 시계열의 톱니/우상향 패턴, GC 지표.

### 대응 제한 시간
- Proposed: 긺(누수는 서서히 진행). 순간 부족형은 짧음.

### 가능한 대응 방법 (≥2)
| 대응 | 장점 | 부작용/비용/복잡도 |
|------|------|--------------------|
| 롤링 재시작(임시) | 즉시 완화 | 근본 미해결, 반복 필요, 운영 부담 |
| 메모리 상향(수직) | 붕괴 지연 | 비용↑, 누수면 결국 재발 |
| 누수 수정 배포 | 근본 해결 | 개발 시간, 배포 리스크(EVT-DEP-001) |
| 인스턴스 수평 분산 | 개별 압력 완화 | 비용↑, 누수 자체는 유지 |

### 결과 판정
- 성공 조건: 메모리 안정(추세 평탄) + Latency 정상. 누수형은 수정 배포 성공 필요.
- 부분 성공 조건: 재시작/증설로 버티되 누수 미수정 → 주기적 재발.
- 실패 조건: OOM으로 서버 Down(EVT-SRV-001) 전이.

### 결과 영향
- 즉시 결과: 성공 시 안정화. 실패 시 다운·데이터 처리 중단.
- 지연 후폭풍 (P6): 임시 재시작 반복 시 직원 피로도(Team Fatigue) 증가, 기술 부채 누적.
- 보상: 근본 수정 시 기술 부채 감소, 안정성 신뢰 회복.
- 페널티: 반복 임시대응 시 피로도·부채↑.

### 반복 제어
- 쿨다운: Proposed 보통.
- 동시 발생 가능: EVT-APP-001, EVT-DEP-001.
- 동시 발생 금지: 동일 서버 메모리 중복 인스턴스.
- 반복 방지 조건: 누수 수정 배포 성공 시 완전 해제; 임시대응은 주기적 재무장.

### 난이도별 수치
| 항목 | Easy | Normal | Hard | 상태 |
|------|------|--------|------|------|

## EVT-DB-001 DB Connection Pool 고갈

- 이벤트 유형: 기술 장애
- 관련 기술: PostgreSQL, App Scaling
- 적용 게임 단계: 2~3
- 이벤트 목적: App 확장이 DB 커넥션으로 전가되는 **파생 병목(P6)**을 체감. 상류 해결이 하류 장애를 만든다.

### 발동 조건 (Trigger)
- DB Connection 사용률 ≥ Critical(Proposed: 95%)에 도달, 신규 커넥션 대기/거부 발생.
- 흔한 선행: App 수평 확장 또는 트래픽 급증으로 커넥션 요구 총량 증가.

### 발동 제외 조건
- Connection 사용률 Warning(Confirmed 방향: 80%) 미만.
- 커넥션 풀 미구성(단일 연결) 초기 단계.

### 사전 징후
- Connection 사용률 80% 초과 → Warning 상태(마스터 플랜 FE-12/4.16 정렬).
- 커넥션 획득 대기 시간 증가, 간헐 Timeout.

### 플레이어가 확인할 수 있는 정보
- 모니터링 없을 때: 일부 요청만 실패/지연(재현 어려움).
- 모니터링 있을 때: Connection 사용률, 대기 큐, 활성/유휴 커넥션 수.

### 대응 제한 시간
- Proposed: 짧음. 95% 도달 후 급격히 오류 확산.

### 가능한 대응 방법 (≥2)
| 대응 | 장점 | 부작용/비용/복잡도 |
|------|------|--------------------|
| Connection Pool 크기 확대 | 즉시 완화 | DB CPU/메모리 부담↑ → EVT-DB-002(Slow Query) 유발 가능(P6) |
| 커넥션 사용 최적화(짧게 잡기) | 근본 개선 | 개발 시간 소요 |
| Redis 캐시 도입/확대 | DB 조회 자체 감소 | 캐시 계열 장애(EVT-CACHE-*) 위험, 도입 비용 |
| Read Replica(단계 3) | 읽기 분산 | 복제 지연·복잡도↑(단계 게이트) |
| 요청 Rate Limit | 즉시 압력 감소 | 사용자 경험 저하 |

### 결과 판정
- 성공 조건: Connection 사용률 안전(Proposed: ≤70%), 대기·Timeout 해소.
- 부분 성공 조건: 풀만 키워 버팀 → DB 자원 압박 전가(후속 위험).
- 실패 조건: 커넥션 고갈 지속, 대규모 Timeout, 서비스 사실상 다운.

### 결과 영향
- 즉시 결과: 성공 시 오류 해소. 실패 시 매출·신뢰도 급락.
- 지연 후폭풍 (P6): 풀 확대만으로 대응 시 DB CPU 포화 → Slow Query·DB 다운 위험.
- 보상: 캐시/최적화 근본 대응 시 안정성·비용 개선.
- 페널티: 무분별 풀 확대 시 운영 복잡도·후속 장애.

### 반복 제어
- 쿨다운: Proposed 보통.
- 동시 발생 가능: EVT-APP-001, EVT-DB-002, EVT-EXT-003.
- 동시 발생 금지: 동일 DB 커넥션 중복 인스턴스.
- 반복 방지 조건: 커넥션 요구 총량이 풀 용량 대비 안전 마진 복귀 시 재무장.

### 난이도별 수치
| 항목 | Easy | Normal | Hard | 상태 |
|------|------|--------|------|------|
| Warning 사용률 | 80% | 80% | 75% | Proposed(Warning 80% 방향은 Program 정렬) |
| Critical 사용률 | 97% | 95% | 90% | Proposed |
| 성공 목표 사용률 | 75% | 70% | 60% | Proposed |

### Simulation 인터페이스
- 입력: 활성/유휴/대기 커넥션, 풀 크기, App 인스턴스 수, RPS, 캐시 Hit율.
- 출력: 사용률·대기 지표, 이벤트 상태, 성공·실패 판정, DB 자원 파생 부하 신호.

### Acceptance Criteria
- AC: DB Connection 사용률이 Warning 기준(80%)을 넘으면 경고 상태가 발생해야 한다.
- AC: App 수평 확장 후 커넥션 총량 증가가 사용률에 반영되어야 한다(P6).
- AC: 풀만 확대해 대응하면 DB 자원 부담 증가 신호가 출력되어야 한다.

### 미확정 사항 / Program 승인 상태
- 미확정: Critical 임계·성공 목표 수치, Read Replica 단계 게이트.
- 승인 상태: Program Review.

## EVT-DB-002 Slow Query

- 이벤트 유형: 기술 장애
- 관련 기술: PostgreSQL
- 적용 게임 단계: 2~3
- 이벤트 목적: 인프라 증설로 풀리지 않는 **쿼리/인덱스 차원의 병목**을 진단하는 경험. "돈으로만 해결되지 않는 문제".

### 발동 조건 (Trigger)
- 특정 쿼리 평균 실행 시간 ≥ 임계(Proposed: 보통 대비 3×) + 호출 빈도 높음.
- 또는 데이터 증가로 풀스캔 발생(인덱스 부재).

### 발동 제외 조건
- 느린 쿼리 호출 빈도가 낮아 전체 영향 미미.
- 최근 인덱스/쿼리 개선 직후.

### 사전 징후
- 특정 엔드포인트 Latency만 선택적으로 상승.
- DB CPU 상승, 트레이스에서 특정 스팬 지연 집중.

### 플레이어가 확인할 수 있는 정보
- 모니터링 없을 때: 전체가 아니라 특정 기능만 느림(원인 특정 어려움).
- 모니터링 있을 때: 트레이스의 쿼리 스팬 지연, 쿼리별 실행 시간/호출 수, DB CPU.

### 대응 제한 시간
- Proposed: 보통. 트래픽 증가 시 악화 가속.

### 가능한 대응 방법 (≥2)
| 대응 | 장점 | 부작용/비용/복잡도 |
|------|------|--------------------|
| 인덱스 추가 | 큰 개선, 저비용 | 쓰기 성능·저장공간 소폭 부담 |
| 쿼리 최적화/재작성 | 근본 개선 | 개발 시간 소요 |
| Redis 캐시로 결과 캐싱 | 조회 부하 감소 | Stale Cache(EVT-CACHE-003) 위험 |
| DB 사양 상향 | 임시 완화 | 비용↑, 근본 미해결 |
| 기능 제한/Rate Limit | 즉시 완화 | 사용자 경험 저하 |

### 결과 판정
- 성공 조건: 해당 쿼리 실행 시간·엔드포인트 Latency 정상 범위 복귀.
- 부분 성공 조건: 캐시로 체감 개선했으나 원 쿼리 미개선(캐시 만료 시 재노출).
- 실패 조건: DB CPU 포화로 전면 지연, Timeout 확산.

### 결과 영향
- 즉시 결과: 성공 시 Latency 회복. 실패 시 신뢰도·매출 손실.
- 지연 후폭풍 (P6): 캐시로만 덮으면 Stale Cache/Cache Miss 계열 위험 이전.
- 보상: 인덱스/최적화 시 기술 부채 감소.
- 페널티: 사양 상향만 반복 시 비용↑, 부채 잔존.

### 반복 제어
- 쿨다운: Proposed 보통.
- 동시 발생 가능: EVT-DB-001, EVT-CACHE-001.
- 동시 발생 금지: 동일 쿼리 중복 인스턴스.
- 반복 방지 조건: 근본 개선(인덱스/쿼리) 시 완전 해제; 캐시 임시대응은 만료 시 재무장.

### 난이도별 수치
| 항목 | Easy | Normal | Hard | 상태 |
|------|------|--------|------|------|
| 느린 쿼리 배수 임계 | 4× | 3× | 2× | Proposed |

- 출력: 쿼리 지연 지표, 이벤트 상태, 성공·실패 판정, 캐시 전가 위험 신호.

### Acceptance Criteria

## EVT-CACHE-001 Redis Cache Miss 증가

- 이벤트 유형: 기술 장애
- 관련 기술: Redis, PostgreSQL
- 적용 게임 단계: 3
- 이벤트 목적: 캐시 Hit율 저하가 DB 부하로 직결됨을 체감. 캐시는 "설정만 하면 되는 것"이 아님을 학습.

### 발동 조건 (Trigger)
- Cache Hit Rate ≤ 임계(Proposed: 70%)가 지속 시간(Proposed: 보통) 이상.
- 흔한 원인: TTL 과소 설정, 키 설계 오류, 캐시 용량 부족으로 잦은 eviction.

### 발동 제외 조건
- Redis 미도입 단계.
- Hit Rate가 임계 초과로 안정.

### 사전 징후
- Cache Hit Rate 하락 추세, DB 조회량·DB CPU 동반 상승.
- Redis 메모리 사용률/eviction 카운트 증가.

### 플레이어가 확인할 수 있는 정보
- 모니터링 없을 때: 캐시를 넣었는데도 DB가 여전히 바쁨(효과 체감 안 됨).
- 모니터링 있을 때: Cache Hit/Miss율, eviction 수, DB 조회량 상관.

### 대응 제한 시간
- Proposed: 보통. 방치 시 DB 병목(EVT-DB-001/002)으로 전이.

### 가능한 대응 방법 (≥2)
| 대응 | 장점 | 부작용/비용/복잡도 |
|------|------|--------------------|
| TTL/캐시 정책 조정 | Hit율 개선 | 과도 TTL 시 Stale Cache(EVT-CACHE-003) 위험 |
| 캐시 키 설계 개선 | 근본 개선 | 개발 시간 소요 |
| Redis 메모리 증설 | eviction 감소 | 비용↑ |
| 캐시 대상 범위 확대 | DB 부하↓ | 정합성 관리 부담↑, 복잡도↑ |

### 결과 판정
- 성공 조건: Hit Rate ≥ 목표(Proposed: 90%), DB 조회량 안정.
- 부분 성공 조건: Hit율 개선했으나 TTL 과도로 정합성 리스크 증가.
- 실패 조건: Hit율 지속 저하, DB 병목 전이.

### 결과 영향
- 즉시 결과: 성공 시 DB 부하·Latency 회복.
- 지연 후폭풍 (P6): 무리한 TTL 상향으로 Stale Cache 유발; 범위 확대 시 무효화 누락 위험.
- 보상: 키/정책 근본 개선 시 안정성·비용 개선.
- 페널티: 증설만 반복 시 비용↑.

### 반복 제어
- 쿨다운: Proposed 보통.
- 동시 발생 가능: EVT-DB-001, EVT-DB-002, EVT-CACHE-002.
- 동시 발생 금지: 동일 캐시 클러스터 중복 인스턴스.
- 반복 방지 조건: Hit율 목표 안정 유지 시 재무장 해제.

### 난이도별 수치
| 항목 | Easy | Normal | Hard | 상태 |
|------|------|--------|------|------|
| 발동 Hit율 임계 | 65% | 70% | 78% | Proposed |
| 성공 목표 Hit율 | 85% | 90% | 93% | Proposed |

### Simulation 인터페이스
- 입력: Cache Hit/Miss, eviction, TTL, Redis 메모리, DB 조회량.
- 출력: Hit율 지표, 이벤트 상태, 성공·실패 판정, Stale 위험 신호.

### Acceptance Criteria
- AC: Cache Hit Rate가 설정 기준 이하로 일정 시간 유지되면 Cache Miss 이벤트 후보가 되어야 한다.
- AC: Hit율 개선이 DB 조회량 감소로 이어지는 상관이 메트릭에 반영되어야 한다.
- AC: TTL을 과도하게 늘려 대응하면 Stale 위험 신호가 출력되어야 한다.

### 미확정 사항 / Program 승인 상태
- 미확정: Hit율 임계 확정.
- 승인 상태: Program Review.

## EVT-CACHE-002 Cache Stampede

- 이벤트 유형: 기술 장애
- 관련 기술: Redis, PostgreSQL
- 적용 게임 단계: 3
- 이벤트 목적: 인기 키 만료 순간 다수 요청이 동시에 DB로 몰리는 순간 폭발형 장애를 체감. 트래픽이 높을수록 위험.

### 발동 조건 (Trigger)
- 고빈도(hot) 키 만료·무효화 순간 + 동시 요청 수 ≥ 임계(Proposed: 상대적 "높음").
- 캐시 재생성 보호(락/조기 재계산) 미적용.

### 발동 제외 조건
- 트래픽이 낮아 동시성 미달.
- 스탬피드 보호(single-flight/lock, jittered TTL) 적용 상태.

### 사전 징후
- 특정 hot 키 만료 주기와 DB 조회 스파이크의 동기화 패턴.
- 만료 직후 순간 DB CPU/커넥션 급등.

### 플레이어가 확인할 수 있는 정보
- 모니터링 없을 때: 주기적으로 순간 장애(스파이크)만 관측, 원인 불명.
- 모니터링 있을 때: 캐시 만료 이벤트와 DB 조회 스파이크의 시간 상관, 커넥션 순간 급등.

### 대응 제한 시간
- Proposed: 짧음(순간형). 사전 예방 성격이 강함.

### 가능한 대응 방법 (≥2)
| 대응 | 장점 | 부작용/비용/복잡도 |
|------|------|--------------------|
| 재생성 락(single-flight) | 근본 방지 | 구현 복잡도↑, 약간의 지연 |
| TTL 지터(jitter) 적용 | 만료 분산, 저비용 | 캐시 신선도 편차 |
| 조기 재계산(pre-refresh) | 만료 전 갱신 | 리소스 상시 소비 |

- 페널티: 실패 시 사용자 신뢰도 하락.

### 반복 제어
- 쿨다운: Proposed 짧음(순간형이라 반복 위험 큼 → 재무장 조건 엄격).
- 동시 발생 가능: EVT-DB-001, EVT-EXT-002/003.

## EVT-CACHE-003 Stale Cache

- 이벤트 유형: 기술 장애
- 관련 기술: Redis
- 적용 게임 단계: 3
- 이벤트 목적: 성능(캐시)과 정합성(신선도)의 트레이드오프를 체감. 잘못된 데이터가 사용자 신뢰를 깎는 경험.

### 발동 조건 (Trigger)
- 원본 데이터 변경(예: 가격/재고 변경) 후 무효화 누락 또는 TTL 과도로 캐시가 옛 값 제공.
- 오래된 값 제공 비율 ≥ 임계(Proposed: 상대 "감지 가능 수준") 지속.

### 발동 제외 조건
- 쓰기 시 무효화/갱신 정책이 올바로 적용됨.
- 캐싱 대상이 정적 데이터(신선도 무관).

### 사전 징후
- 데이터 변경 직후에도 이전 값 노출 로그.
- 사용자 문의/불일치 신호(신뢰도 하락 조짐), 화면-DB 값 불일치.

### 플레이어가 확인할 수 있는 정보
- 모니터링 없을 때: 사용자 신뢰도만 원인 불명으로 하락.
- 모니터링 있을 때: 캐시 값과 원본 값 불일치 로그, 무효화 이벤트 누락 지표.

### 대응 제한 시간
- Proposed: 보통. 방치 시 신뢰도 지속 하락.

### 가능한 대응 방법 (≥2)
| 대응 | 장점 | 부작용/비용/복잡도 |
|------|------|--------------------|
| 쓰기 시 캐시 무효화(write-through/invalidate) | 근본 해결 | 구현 복잡도↑, 쓰기 지연 소폭 |
| TTL 축소 | 간단, 신선도↑ | Hit율 하락 → EVT-CACHE-001 위험(P6) |
| 이벤트 기반 무효화(pub/sub) | 정밀 무효화 | 설계 복잡도↑ |
| 해당 항목 캐싱 제외 | 정합성 확실 | DB 부하↑ |

### 결과 판정
- 성공 조건: 데이터 변경 후 캐시 값이 신선하게 반영, 불일치 비율 정상.
- 부분 성공 조건: TTL 축소로 완화했으나 Hit율 하락(다른 위험 증가).
- 실패 조건: 불일치 지속으로 사용자 신뢰도 붕괴 근접.

### 결과 영향
- 즉시 결과: 성공 시 정합성 회복.
- 지연 후폭풍 (P6): TTL 축소 남발 시 Cache Miss 증가로 DB 부하 전가.
- 보상: 무효화 근본 적용 시 신뢰도 회복.
- 페널티: 방치 시 사용자 신뢰도 하락(가중), 데이터 신뢰 이슈.

### 반복 제어
- 쿨다운: Proposed 보통.
- 동시 발생 가능: EVT-CACHE-001.
- 동시 발생 금지: 동일 캐시 항목 중복 인스턴스.
- 반복 방지 조건: 무효화 정책 적용 시 완전 해제.

### 난이도별 수치
| 항목 | Easy | Normal | Hard | 상태 |
|------|------|--------|------|------|
| 신뢰도 하락 속도 | 느림 | 보통 | 빠름 | Proposed |
| 감지 지연 | 김 | 보통 | 짧음 | Proposed |

### Simulation 인터페이스
- 입력: 원본 변경 이벤트, 캐시 값/TTL, 무효화 정책 상태, 조회 비율.
- 출력: 불일치 비율, 신뢰도 영향, 이벤트 상태, 성공·실패 판정.

### Acceptance Criteria
- AC: 원본 데이터 변경 후 무효화 누락 시 캐시-원본 불일치가 로그로 확인 가능해야 한다.
- AC: 무효화 정책 적용 후 불일치 비율이 정상으로 회복되어야 한다.
- AC: TTL만 줄여 대응하면 Cache Hit율 하락 위험 신호가 출력되어야 한다.

### 미확정 사항 / Program 승인 상태
- 미확정: 신뢰도 하락 계수(GD-012 밸런스).
- 승인 상태: Program Review.

- 보상: 성공 시 매출·투자자 신뢰 대폭 상승, 챕터 진행.
- 페널티: 실패 시 대형 손실(게임 오버 근접 가능, 4.15).

### 반복 제어
- 쿨다운: 캠페인 스케줄 기반(연 1회성 성격) → 재무장 엄격.
- 동시 발생 가능: EVT-APP-001, EVT-DB-001, EVT-CACHE-002, EVT-LB-001(복합).
- 동시 발생 금지: 동일 Black Friday 중복.
- 반복 방지 조건: 스케줄 1회성; 다음 사이클까지 재무장 안 함.

### 난이도별 수치
| 항목 | Easy | Normal | Hard | 상태 |
|------|------|--------|------|------|
| 피크 배수 | 3× | 5× | 8× | Proposed |
| 피크 지속 | 짧음 | 보통 | 긺 | Proposed |
| 준비 기간 | 7일 | 3일 | 1일 | Proposed(EVT-D-001) |

### Simulation 인터페이스
- 입력: 스케줄, 준비 조치 목록, 각 계층 용량/보호 설정, 피크 계수.
- 출력: 피크 곡선, 계층별 장애 판정, 복합 결과, 매출/신뢰도 변화, 성공·실패 판정.

### Acceptance Criteria
- AC: Black Friday는 사전 카운트다운/준비 기간과 함께 고지되어야 한다.
- AC: 사전 준비 조치 수준에 따라 피크 기간 장애 발생이 달라져야 한다.
- AC: 피크 기간 무중대장애 통과 시 단계3 승급 조건에 기여해야 한다(Program 확인 필요).

### 미확정 사항 / Program 승인 상태
- 미확정: 준비 기간(EVT-D-001), 피크 배수·지속, 승급 연계(Program).
- 승인 상태: Program Review.

## EVT-EXT-004 금요일 배포

- 이벤트 유형: 외부 상황 / 운영 리스크 수식(modifier)
- 관련 기술: 배포, Rollback
- 적용 게임 단계: 1~3
- 이벤트 목적: 배포 타이밍의 위험(대응 인력·시간 제약)을 체감. "언제 배포하는가"도 의사결정.

### 발동 조건 (Trigger)
- 게임 시간상 주말 직전(금요일 후반)에 배포를 실행할 때 리스크 수식 적용.
- 이 이벤트는 단독 장애가 아니라 EVT-DEP-001 실패 확률/대응 여건에 **수식(modifier)**으로 작용.

### 발동 제외 조건
- 배포 미실행.
- 주중 배포(수식 미적용).

### 사전 징후
- 배포 예약 시 "주말 임박" 경고 표기(대응 여건 축소 안내), CTO 코멘트(가디언 경고).

### 플레이어가 확인할 수 있는 정보
- 모니터링 없을 때: 배포는 동일해 보이나 문제 시 대응 지연.
- 모니터링 있을 때: 배포 리스크 표시, 예상 대응 여건(주말 인력/시간 축소).

### 대응 제한 시간
- Proposed: 배포 실패 발생 시 대응 창이 평소보다 짧게 적용(수식).

### 가능한 대응 방법 (≥2)
| 대응 | 장점 | 부작용/비용/복잡도 |
|------|------|--------------------|
| 배포를 주중으로 연기 | 리스크 회피 | 기능 출시 지연 |
| 강행 + 자동 롤백 안전장치 강화 | 출시 유지, 피해 최소화 | 사전 준비 비용 |
| 강행(무대비) | 즉시 출시 | 실패 시 피해·피로도 가중 |
| 카나리 축소 배포 | 리스크 국소화 | 관리 복잡 |

### 결과 판정
- 성공 조건: 배포 정상 + 문제 미발생(또는 신속 대응 성공).
- 부분 성공 조건: 문제 발생했으나 안전장치로 피해 최소화.
- 실패 조건: 주말 대응 지연으로 장애 장기화, 피로도 급증.

### 결과 영향
- 즉시 결과: 성공 시 기능 출시 이득.
- 지연 후폭풍 (P6): 실패 시 EVT-DEP-001 페널티 가중 + 직원 피로도 큰 폭 상승.
- 보상: 안전한 배포 문화 확립 시 장기 안정.
- 페널티: 반복 강행 실패 시 피로도·이탈 위험(4.15).

### 반복 제어
- 쿨다운: 배포 트리거 기반(수식이므로 별도 쿨다운 없음).
- 동시 발생 가능: EVT-DEP-001(주 연계), EVT-APP-002.
- 동시 발생 금지: 해당 없음(수식형).
- 반복 방지 조건: 배포 시점 선택으로 플레이어가 제어.

### 난이도별 수치
| 항목 | Easy | Normal | Hard | 상태 |
|------|------|--------|------|------|
| 실패 확률 가중 | ×1.2 | ×1.5 | ×2.0 | Proposed |
| 대응 창 축소 | 소폭 | 보통 | 큼 | Proposed |
| 피로도 가중 | 소폭 | 보통 | 큼 | Proposed |

### Simulation 인터페이스
- 입력: 배포 시각(게임 시간), 안전장치 설정, EVT-DEP-001 상태.
- 출력: 적용된 리스크 수식값, 대응 창 축소량, 피로도 영향, 성공·실패 판정.

### Acceptance Criteria
- AC: 주말 임박 시점에 배포하면 배포 실패 확률/대응 여건에 수식이 적용되어야 한다.
- AC: 배포 예약 시 주말 임박 경고가 표시되어야 한다.
- AC: 주중 배포에는 이 수식이 적용되지 않아야 한다.

### 미확정 사항 / Program 승인 상태
- 미확정: 게임 시간 단위(GD-001)와 "금요일" 정의, 수식 계수.
- 승인 상태: Program Review.

## EVT-EXT-005 클라우드 비용 증가

- 이벤트 유형: 외부 상황
- 관련 기술: 비용(전 인프라)
- 적용 게임 단계: 2~3
- 이벤트 목적: 무분별한 증설의 장기 비용을 체감. 효율(최적화)과 규모의 균형을 학습.

### 발동 조건 (Trigger)
- 서버 비용 총액이 매출 대비 임계(Proposed: 상대 "비중 과다") 초과 지속.
- 또는 외부 요금 인상 이벤트(저확률, 사전 고지).

### 발동 제외 조건
- 비용 비중이 안전 범위.
- 최근 비용 최적화 직후.

### 사전 징후
- 서버 비용 곡선 우상향, 매출 대비 비용 비중 경고 게이지.
- 유휴 자원(낮은 CPU에 다수 인스턴스) 지표.

### 플레이어가 확인할 수 있는 정보
- 모니터링 없을 때: 자금이 서서히 마름(원인 분산).
- 모니터링 있을 때: 비용 구성(노드별), 유휴율, 비용/매출 비중 추이.

### 대응 제한 시간
- Proposed: 긺(서서히 압박).

### 가능한 대응 방법 (≥2)
| 대응 | 장점 | 부작용/비용/복잡도 |
|------|------|--------------------|
| 과잉 인스턴스 축소 | 비용 절감 | 트래픽 재증가 시 여유 부족 |
| 최적화로 자원 효율↑ | 근본 절감 | 개발 시간 |
| 캐시로 DB 부하↓(사양 다운) | 비용·성능 동시 | 캐시 계열 위험 |
| 요금제/예약 인스턴스 조정 | 단가 절감 | 유연성 저하(약정) |
| 방치 | 대응 비용 0 | 자금 압박 지속(파산 위험, 4.15) |

### 결과 판정
- 성공 조건: 비용/매출 비중 안전 범위 복귀, 성능 유지.
- 부분 성공 조건: 비용은 줄였으나 여유 축소로 트래픽 리스크 증가.
- 실패 조건: 비용 압박 지속으로 자금 감소 → 파산 위험.

### 결과 영향
- 즉시 결과: 성공 시 자금 흐름 개선.
- 지연 후폭풍 (P6): 과도 축소 시 다음 트래픽 이벤트에서 용량 부족(EVT-APP-001).
- 보상: 효율화 시 자금 여유·투자자 신뢰.
- 페널티: 방치 시 지속 자금 유출.

### 반복 제어
- 쿨다운: Proposed 긺.
- 동시 발생 가능: EVT-EXT-001/003(증설 유발과 상충).
- 동시 발생 금지: 동일 비용 경고 중복.
- 반복 방지 조건: 비용 비중 안전 복귀 시 재무장 해제.

### 난이도별 수치
| 항목 | Easy | Normal | Hard | 상태 |
|------|------|--------|------|------|
| 비용/매출 비중 경고 | 60% | 50% | 40% | Proposed |
| 외부 요금 인상 확률 | 매우 낮음 | 낮음 | 보통 | Proposed |

### Simulation 인터페이스
- 입력: 노드별 비용, 유휴율, 매출, 요금제, 외부 인상 시드.
- 출력: 비용/매출 비중, 유휴 지표, 자금 추이, 이벤트 상태, 성공·실패 판정.

### Acceptance Criteria
- AC: 서버 비용/매출 비중이 경고 기준을 넘으면 비용 경고 상태가 표시되어야 한다.
- AC: 과잉 인스턴스 축소 시 비용 감소가 자금 흐름에 반영되어야 한다.
- AC: 과도 축소 후 트래픽 증가 시 용량 부족 위험 신호가 출력되어야 한다.

### 미확정 사항 / Program 승인 상태
- 미확정: 비용 비중 임계, 외부 인상 확률.
- 승인 상태: Program Review.

## 이벤트 간 연쇄 구조 (Chains)

연쇄 구조 상세 규칙은 [event-design-standard.md](./event-design-standard.md) §6·§7을 따른다. 과도한 연쇄 장애를 막기 위해 **최대 연쇄 깊이**와 **차단 조건**을 명시한다.

### CHN-001 트래픽 급증 → 계층 연쇄
- 선행 이벤트: EVT-EXT-001/002/003 (유입 증가)
- 연쇄: 유입↑ → EVT-APP-001(App CPU) → App 증설 → DB 커넥션↑ → EVT-DB-001(Pool 고갈) → 풀 확대 → DB CPU↑ → EVT-DB-002(Slow Query) → API Timeout
- 연쇄 발동 조건: 각 단계의 개별 발동 임계 충족 + 상류 대응이 하류로 부하 전가(P6).
- 연쇄 차단 조건: 어느 단계든 **근본 대응**(최적화/캐시/커넥션 튜닝) 시 하류 전이 차단.
- 플레이어가 확인할 수 있는 징후: 단계별 Warning이 상류→하류로 순차 점등.
- 최대 연쇄 깊이: Proposed 4단계.
- 과도 연쇄 방지: 깊이 초과 시 신규 하류 이벤트 발동 대신 기존 이벤트 심화로 처리(무한 연쇄 금지).

### CHN-002 캐시 오용 연쇄
- 선행 이벤트: Redis 도입 → DB 조회 부하 감소 → 가격/데이터 변경
- 연쇄: 무효화 누락 → EVT-CACHE-003(Stale Cache) → 사용자 신뢰도↓ ; 또는 TTL 과소 → EVT-CACHE-001(Miss↑) → DB 부하↑
- 연쇄 발동 조건: 캐시 정책 결함 + 데이터 변경/트래픽 조건.
- 연쇄 차단 조건: 올바른 무효화 정책·키 설계 적용.
- 플레이어가 확인할 수 있는 징후: 캐시 지표(Hit율/불일치 로그)와 신뢰도/ DB 부하의 상관.
- 최대 연쇄 깊이: Proposed 3단계.
- 과도 연쇄 방지: 신뢰도 하락은 이벤트당 상한 적용(급락 방지, GD-012).

### CHN-003 배포 리스크 연쇄
- 선행 이벤트: EVT-EXT-004(금요일 배포 수식) → EVT-DEP-001(배포 실패)
- 연쇄: 실패 → (미대응) → EVT-APP-002(누수형 재배포) 또는 EVT-SRV-001(다운) → 피로도↑
- 연쇄 차단 조건: 신속 Rollback + 원인 규명.
- 최대 연쇄 깊이: Proposed 3단계.
- 과도 연쇄 방지: 롤백 성공 시 즉시 연쇄 종료.

> 연쇄의 절대 시간·깊이 수치는 GD-001·GD-012 확정 후 조정 대상. 현재 모두 Proposed.
