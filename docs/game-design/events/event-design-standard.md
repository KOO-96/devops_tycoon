# 이벤트 설계 표준 (Event Design Standard)

> 이 문서는 DevOps Tycoon의 **모든 이벤트가 따라야 할 공통 템플릿과 규칙**을 정의합니다.
> 개별 이벤트 데이터는 [mvp-event-catalog.md](./mvp-event-catalog.md)에 작성합니다.

- 문서 버전: v0.1.0
- 작성 브랜치: `plan/event`
- 최종 수정일: 2026-07-20
- 담당 역할: Event
- 문서 상태: **Draft**
- 참고한 Program 문서: `origin/plan/program:docs/game-design/devops-tycoon-master-plan.md` (commit `a28fd84`)

## 1. 설계 원칙 (Program 정렬)

이 표준은 Program 마스터 플랜의 다음 원칙과 게이트를 강제한다.

- **P4 — 복수 정답:** 모든 장애 이벤트는 서로 다른 트레이드오프의 대응을 **2개 이상** 가진다.
- **P5 — 무료 개선 없음:** 모든 기술 도입은 자금 / 운영 복잡도(Ops Complexity) / 기술 부채(Tech Debt) 중 **최소 하나**를 증가시킨다.
- **P6 — 파생 병목:** 상류 병목 해소가 하류 부하로 전가될 수 있음을 후폭풍으로 정의한다.
- **P7 — 선행 징후:** 모든 장애는 발동 전 **관측 가능한 사전 징후**를 노출한다. 무징후 즉사 금지.
- **P8 — Simulation 권위:** 이벤트 발동 조건·수치는 Simulation이 계산한다. Event 문서에 없는 규칙을 Simulation이 임의 추가하지 않으며, Event도 관측 불가한 사실을 확정하지 않는다.
- **EV-1~10 승인 게이트:** 마스터 플랜 4.13의 10개 기준을 모두 충족해야 병합 승인된다.

> 노드 상태 표기는 마스터 플랜 4.9와 동일하게 `Healthy / Warning / Critical / Down`을 사용한다.

## 2. ID 명명 규칙

형식: `EVT-<도메인>-<3자리 일련번호>`

| 도메인 코드 | 의미 |
|-------------|------|
| `LB` | Load Balancer |
| `APP` | App Server (스케일/CPU/메모리) |
| `DB` | PostgreSQL |
| `CACHE` | Redis / 캐시 계층 |
| `DEP` | 배포 / CI/CD / Rollback |
| `SRV` | 서버 인프라(다운 등) |
| `HC` | Health Check |
| `EXT` | 외부 상황(마케팅·트래픽·비용) |
| `CHN` | 연쇄(Chain) 정의 |

연쇄 정의 ID는 `CHN-<3자리>`를 사용한다(예: `CHN-001`).

## 3. 이벤트 상태 값

| 상태 | 의미 |
|------|------|
| Draft | Event 담당자 작성 중 |
| Program Review | Program 검토 대기 |

## 5. 수치 상태 규칙 (마스터 플랜 4.18·GD-012 정렬)

모든 수치에는 상태 라벨을 붙인다.

| 상태 | 의미 |
|------|------|
| Confirmed | Program에서 승인된 값 |
| Proposed | Event 담당자가 제안한 초기값(근거 필수) |
| TBD | 추가 결정 필요(program-decisions-required.md 등록) |

수치 제안 시 함께 기록: **제안 이유 / 예상 플레이 영향 / 난이도별 변경 가능성 / Simulation 테스트 필요 부분**.

> 수치는 코드 상수로 직접 넣지 않고 **밸런스 데이터(설정 파일)로 분리 가능**하도록 정의한다. 이는 데이터 구조 요구이며 구현 방식을 강제하지 않는다.

---

## 6. 사전 징후·대응 시간 규칙 (P7 / EV-1·EV-3)

- 모든 장애 이벤트는 `Warning` 단계를 거쳐 `Critical`로 악화한다. `Healthy → Down` 직행 금지(예외: 명시적으로 정의된 하드 크래시도 직전 관측 지표를 남긴다).
- `대응 제한 시간`은 "사전 징후 최초 노출 시점 ~ 실패 판정 시점" 사이의 게임 시간으로 정의한다.
- 대응 제한 시간의 절대값은 게임 시간 단위(GD-001) 확정에 의존하므로 다수가 `TBD`이며, **상대적 여유(짧음/보통/긺)**를 함께 표기한다.

---

## 7. 결정론·반복 제어 규칙 (EV-9 / Simulation 정렬)

- 이벤트 발동은 Seed 기반 결정론을 따른다: **동일 Seed + 동일 명령 순서 → 동일 이벤트 시퀀스.**
- 확률적 발동을 쓰는 경우, 난수는 Seed 기반 PRNG에서 도출한다(실시간 난수 금지).
- 쿨다운 중 동일 `Event ID`는 재발동하지 않는다.
- `반복 방지 조건`으로 1회성(one-shot) / 조건 재무장(re-arm) / 최대 발생 횟수를 명시한다.

---

## 8. 이벤트 vs 역할 경계

- **Event:** 상황·기술 필요성·발동 조건·사전 징후·대응 선택지·결과·초기 수치(Proposed)를 설계한다.
- **Program:** MVP 범위·게임 방향·최종 승인을 결정한다.
- **Simulation:** 승인된 조건·수치를 계산하고, 문서에 없는 규칙을 임의 추가하지 않는다.
- **금지:** Event 문서에 실제 k3s 운영 설정을 작성하지 않는다. 게임 속 인프라(콘텐츠)와 실제 운영 인프라를 혼동하지 않는다.
